## 3. 我核对出来的问题

1. **公式自检没做完**：`本港侧` 依赖 `装港是否本港`，而这个查找引用还没建，所以 `本港侧`、`本港等泊（天）`、`本港作业（天）` 三个公式当时算不出结果。报告里这三项只写了预期值，真正读回来验证的只有 `实际航程（天）`（5.77）和 `拼船`（否）。手工建好 4 个查找引用后，必须重跑一次自检（提示词见 `base-verify-agent-prompt.md`）。
2. **Base 里原本就有 17 张企微历史表**（共 1 万多条记录），不在我们的计划里，也没被动过。需要你确认：它们是你为迁移准备的吗？如果是，迁移脚本可以直接通过接口读这些表，不用再读 Excel，我会据此调整迁移方案。它们含真实业务数据，所以这个 Base 更要坚持只对应用和系统管理员开放。
3. **建表过程中 agent 做过很多试建实验**（试建 T01、自动编号、双向关联、空单选等）。报告只说「新建数据表 10 张」，没说试验用的表和字段有没有清掉。预期 Base 里现在是 17 + 11 = 28 张表，如果多了，就是试验残留，需要清理。
4. **T01 种子数据和计划不一致**：计划写的是中文名「巴浩多比」，agent 写成了「莫罗瓦利（IMIP）」，别名里多了「德信本港」。这可能是 agent 从 Base 里原有的「港口信息表」读来的，如果是，以真实数据为准更好；但页面和自然语言解析里用的是「巴浩多比」，别名里要包含它。请你确认本港的中文名，我再对齐代码里的别名。
5. **高级权限（系统写入字段设为只读）这一步可以取消**：因为 Base 只对应用和系统管理员开放，业务员根本看不到也改不了表格，不需要再设字段只读。

## 5. 第二轮核对结果（2026-11-05，本机 agent 只读核对 + 公式自检）

结论：

- Base 里共 28 张表：计划的 11 张齐全 + 17 张企微历史表（表名与 `docs/data-profile` 一致），**没有任何试验残留**。上面第 3 节的问题 3 已排除。
- 10 张表（T01、T02、T03、T05、T06、T07、T08、T10、T09a、T09b）的字段名称、类型、选项、关联目标与建表计划 100% 一致。T04 只差 4 个查找引用，原因就是你还没在界面里建。
- 3 个公式引用检查有效：T08 的 3 个、T04 的 `装港逾期` `实际航程（天）` `拼船`。
- 端到端读回验证通过的只有 `拼船`（0 条明细 → 否；2 条明细 → 是），说明关联和计数公式工作正常。测试行已全部删除，T04、T05 记录数回到 0。

新发现的问题：

1. **`实际航程（天）` 没有读回数值**：它不依赖任何查找引用，所以不能怪查找引用没建。最可能的原因是我们给的表达式里用了 `DATETIME_DIFF(…, "minute")`，这是 Airtable 的函数，飞书多维表格不一定有。接口接受了表达式，但算不出值。因此 `本港等泊`、`本港作业` 用的同一种写法也可能有同样的问题。诊断和修复提示词见 `base-formula-agent-prompt.md`。
2. **这几个公式不影响业务逻辑**：状态、航程、时长这些衍生值后端自己也会算一份（`server/domain/status.js` 的 `deriveFields`），预测引擎用的是后端算的值。所以公式写错只会影响表格里的显示和兼容表，不会让预测算错。修复它们是为了表格里看到的数字正确。
3. **企微历史表的记录数比原始 Excel 少**：商务海运船舶动态表 Base 里 289 行（导出摘要 336 行），大宗到船计划表 591 行（导出摘要 636 行，含空行 643），其余的港口信息表 211、靠船计划表 453、历史副本 3,066 与摘要一致。可能是导入时去掉了空行，也可能不完整。如果迁移要读这些表，得先核对这两张。
