# 外部模型评审：材料与提示词

目的：在写业务代码之前，请另一个大模型从多个角度做一次全面评审，找出会导致返工的问题。我无法验证你所用模型的具体能力、上下文长度和联网读取 GitHub 的方式，下面按最稳妥的做法写。

## 1. 怎么给材料

**推荐方式：上传两份评审包，不依赖仓库权限。**

- `docs/review/review-pack-1-spec.md`（约 7.8 万字）：业务背景导读、项目约定与已锁定规则、实施计划、全部表结构规格、建表清单、待确认事项、数据概况。
- `docs/review/review-pack-2-prototype.md`（约 3.8 万字）：原型说明和四个核心代码文件（预测引擎、状态推导与校验、自然语言解析、库存曲线）。
- 两份都是自包含的，已对内部人名和真实合同号脱敏。需要更新时在仓库根目录执行 `node scripts/build-review-pack.mjs` 重新生成。
- 想让它看原型的样子：再上传 `prototype/screenshots/` 里的几张图，建议 `P11-ask.png`、`P02-prediction.png`、`P02-prediction-stock-urgent.png`、`P03-prediction-detail-stock.png`、`P05-voyage-detail.png`、`P06-capacity-calendar.png`。

**不太推荐：直接给仓库链接。**

- 仓库是私有的话，大多数网页版对话读不到，需要在对应产品里授权连接你的 GitHub 账号，或者把它做成一个临时的只读访问，这些都有泄露面。
- 仓库里的原始文档没有脱敏（`docs/data-profile/` 表头里有内部人名，`docs/implementation-plan.md` 里有人名和合同号），评审包里已经处理过。
- 即使能读仓库，它也可能只读到你给的那几个文件，并不能保证「全部读完」。上传评审包更可控。

**可选：原型网页。** 仓库配置了 GitHub Pages 发布 `prototype/`。如果这个站点是公开可访问的，可以把链接给支持联网浏览的模型让它实际点一遍；如果打不开，就只用截图。

**不要上传**：企微导出的原始 Excel、库存消耗模拟表（含真实业务数据）、任何密钥。

## 2. 三轮评审

不要一次性让它「全面评审」，容易泛泛而谈。分三轮，每一轮在同一个对话里继续。

### 第一轮：理解复述（先验证它读懂了）

把两份评审包上传后，发下面这段：

```text
我会请你对一个尚未写代码的软件项目做一次全面的写前评审。先不要评审，只做两件事。

【材料】我上传了两份文件：评审包 1（业务背景 + 全部规格）和评审包 2（原型说明 + 核心代码）。请完整阅读。如果有任何文件或章节你没能读到，直接告诉我，不要猜。

【任务】
1. 用你自己的话复述这个系统：谁用、解决什么问题、业务流程、三类船、核心数据模型、预测怎么算、库存断料怎么进预测、一期范围和里程碑。控制在 800 字以内，要具体，不要复述标题。
2. 列出你对业务背景「不确定或看不懂」的地方（术语、流程、数字的含义），逐条写明，不要假装懂。
3. 列出材料内部「前后矛盾或口径不一致」的地方，每条给出两处出处。
4. 用一句话说明你认为这个项目最大的风险是什么。

规则：只依据材料，不要把行业常识当成项目事实；用到推测时标「推测」。用中文回答。
```

你看它的复述对不对，不对的地方当场纠正（或者让我补充背景），再进第二轮。

### 第二轮：分域评审（核心）

```text
现在开始评审。你要同时扮演下面七个角色，每个角色独立给出发现，不要互相迎合：
A 航运/大宗贸易业务分析师；B 产品经理；C 企业应用架构师（熟悉飞书多维表格、飞书妙搭、PostgreSQL、Node.js）；D 数据建模与迁移专家；E 预测与规则引擎工程师；F 测试与验收负责人；G 信息安全与数据合规顾问。

【评审目标】在开写业务代码之前，找出「如果现在不改，写代码时会返工或上线后出事」的问题。按返工代价和风险大小排序，而不是按章节顺序。

【约束】
1. 「已锁定业务规则」和访谈决策 K01–K14 是业务方定的，不要建议推翻。如果你对它们有疑虑，只能写在单独的「对锁定项的疑虑」一节，且只限于：执行层面有歧义、相互冲突、无法测试、或在某些场景下会产生明显错误结果；每条要给出具体场景。
2. 原型里的数据全部虚构、泊位容量是示例值，不要评价这些数值本身；原型简化与规格问题请区分开。
3. 当前没有任何功能上线，不要把原型当成已上线系统。
4. 每条发现必须引用出处（评审包的章节或文件名，原型代码给出函数名）。材料里没有的信息，明确说「材料中没有」，不要编造。行业通用做法要标「通用做法」，不要冒充项目事实。
5. 不要写业务代码；可以给伪代码、公式、表结构修改建议。

【重点关注，请逐项回应，没有问题也要写「未发现问题」并说明你检查了什么】
1. 预测规则：
   - 跨路径分流：库存提问的窗口常跨过 15 天界线，原型让每个候选日期各按自己距今天数分流，推荐方案取近 15 天路径的最优、备选方案取 15 天后路径的最优，不跨路径比数值。这是否违背规则 4 和 7 的本意？有更好的做法吗？
   - 候选窗口（3 天一档）、备选方案与推荐方案窗口不重叠、发船日 = 窗口最后一天减 P80、航次表路径用「等效余量」判断 30%，这些设计在边界场景下会不会给出荒谬结果？
   - 「低可信」的定义和降级逻辑是否清晰、可测试。
2. 库存断料：断料日 = 模拟库存首次降到 0 的日期，且序列已含已排定到货，这个理解有哪些失败场景（比如到货延误、库存刚好卡在 0 附近、日耗变化）？缓冲 3 天怎么定？一船多种物料怎么办？库存「品名」与货物明细「物资类别 / 货物名称」的映射怎么设计？
3. 状态推导：取消、大宗船不记录装港靠泊、成品船以卸港靠泊为结束、节点缺失或乱序，这些规则的漏洞和边界。
4. 数据与迁移：港口 295 种写法、MMSI 缺失、航次归并键「船名 + 到港日」、历史副本去重、时区、疑似占位时间，这些清洗规则会不会误伤或漏判？迁移验收 G1 的口径是否足够？
5. 架构与一致性：应用唯一写入口、先写飞书再回写镜像、写入队列单线程、streaming 同步延迟、多维表格限流和单表行数上限、二期切换。找出会导致数据不一致、丢写、重复写、幂等性问题的地方；给出需要补的机制。
6. 权限与隐私：K11 的四个角色与「仓储物流部能登记作业数据、金额只有大宗采购部能看」是否自洽；金额隔离放在应用层而不是多维表格层是否足够；行级安全；日志里是否会泄露金额。
7. 自然语言入口：关键词规则解析的覆盖和误判风险；与已锁定规则 10、11（数值不得被生成式模型改写、已移除 AI 开放问答）的关系；语音输入在飞书里的可行性。
8. 数据模型：T01–T10、D01–D12 有没有缺字段、冗余字段、关联方向不合理、枚举设计问题；多维表格单表 150 个字段、2 万行等限制对 T04（约 3,600 行、每年 +1,500 行）和 T05 的影响。
9. 工作量与里程碑：一期 8 周、M1 数据底座 / M2 预测上线 / M3 并行验收，是否现实？关键路径是什么？哪些前置条件缺失（权限、脚手架、数据映射）会卡住？
10. 验收与测试：G2 要求用 20 个预测用例与老系统逐条对照，请设计这 20 个用例（覆盖三类船、≤15 天与 ＞15 天、无数据、低可信、库存断料、告急），写出输入、期望行为和判定标准；再补充单元测试和数据校验应覆盖的清单。

【输出格式】Markdown，按下面结构：
1. 总体判断（不超过 300 字）：能不能开写？前提是什么？
2. 发现清单。每条一个小节，标题形如「ARCH-03 [P1] 一句话概括」。字段：严重度（P0 阻塞开写 / P1 开写前应决 / P2 可边写边定 / P3 建议）、出处、问题、失败场景（用具体例子）、建议、需要谁确认（业务方 / 产品负责人 / 技术）。
3. 对锁定项的疑虑（仅记录，不要求修改）。
4. 对「待确认事项」每一条的推荐答案和理由（逐条对应，勾掉的不用回答）。
5. 我们没有问、但你认为应该问的 10 个问题。
6. 20 个验收用例设计。
7. 建议的开工前必做清单（按顺序，注明负责人是业务方还是技术）。

篇幅较长可以分几次回复，每次回复末尾写「待续：下一次继续 X」。
```

### 第三轮：汇总与核对（可选，但建议做）

```text
请回头检查你上一轮的输出：
1. 哪些发现你其实没有足够依据（材料里没有明确写，是你推测的）？把这些降级或标注「推测」。
2. 有没有互相重复或冲突的发现？合并。
3. 按「如果只能改 10 件事，先改哪 10 件」排出优先级，说明每一件不改的后果。
4. 把最终结果整理成一份可以保存为 Markdown 的《写前评审报告》，只保留有依据的发现，格式与上一轮一致。
```

## 3. 评审结果怎么带回来

把第三轮的报告原文发给我（或保存为 `docs/review/external-review-YYYYMMDD.md` 提交到仓库）。我会：

1. 逐条核对它引用的出处是否真实、结论是否成立，把站不住脚的挑出来；
2. 把成立的发现分三类：需要你决策的（写入 `docs/open-questions.md`）、需要改规格或建表清单的（直接改文档）、可以写代码时再处理的（记入开发待办）；
3. 把它设计的 20 个验收用例和我们的原型逐条对一遍，能跑的用原型引擎先试跑，看结果是否合理。

## 4. 几点提醒

- 外部模型也会犯错：它可能读漏、可能把推测当事实、可能对飞书平台的能力说错。重要结论我会再核对，平台能力类的结论最好你在飞书里实际验证一次。
- 评审包里有项目的业务规则和数据结构，但没有真实业务数据和人名。你把它交给哪个外部服务，要符合公司的数据使用要求，这一点由你决定。
