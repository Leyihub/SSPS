# 性能检查记录（W53，2026-11-05 云端部分）

方法：在内存 Postgres（PGlite）里直接灌入 3000 条航次、6000 条货物明细，量真实仓储的读路径耗时。数据库在进程内，所以**数字只用来比较查询次数的影响，不代表真实库的延迟**（真实库每次查询还有网络往返，查询次数越少越好）。

**发现并修掉的问题**：航次列表按合同号搜索、兼容表刷新、库存过期判断原来对每个航次各查一次货物明细（3000 个航次 = 3000 次查询，真实库上会是几十秒）。已在航次仓储端口加了 `cargoByVoyage` / `settlementByVoyage` / `salesExtByVoyage` 三个批量读，这些场景都改成每种一次查询。

**修复后（3000 航次 / 6000 明细）**：航次列表 ≈ 0.25 秒（带合同号搜索 ≈ 0.27 秒）；批量读全部货物明细 ≈ 0.13 秒；兼容表全量刷新（读取 + 生成行 + 写假飞书）≈ 0.7 秒。

**还没做 / 需要真实环境确认**

- 真实库的往返延迟（本机联调时用同样的数据量再量一次，本机到应用库约 6 秒的同步延迟是同步任务，不是查询）。
- 列表每次请求都会读全部航次再在内存里过滤分页（航次总数几千条时可以接受；超过几万条再改成数据库端分页）。
- `loadDict`（港口/船舶/泊位字典）每次读请求都会重读，可以加几十秒的内存缓存；写入后要失效。数据量小，暂不做。
- 兼容表向飞书写入受限于每批 500 条、单线程队列；3000 航次约 6000 行 × 87 列，真实 Base 上的耗时要实测，必要时改成只更新有变化的行。
