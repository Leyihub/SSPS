## 11. 逐条复核提示词（审计出报告之后、整改之前发；代码仍在推进时必发）

适用情形：审计周期长、期间代码仍在提交，或汇总报告里的结论来自多个不同提交（例如 2026-11-06 的 00-summary.md：01 读到 2463526，03/09 读到 0c9c784，05 只读到 04825bd，07/08 还带未提交修改，且汇总写“没有执行发布”，而文档仓记录当晚 22:28 已发布）。这一段把「历史发现」转成「针对同一个提交的当前结论」。

```text
你要对 docs/audit/00-summary.md 及 01–09 报告做「基线复核」。目标：把每条发现落到同一个、明确的代码提交上，给出它现在是否仍成立，并修正汇总里已经过时的表述。全程只读，约束同总提示词（不改代码、不碰真实飞书/线上、不读 .env.local、不输出密钥与真实业务数据）。

第 1 步：固定基线
- 记录代码仓 HEAD、是否有未提交修改、文档仓 HEAD、当前时间。若代码仓不干净，说明哪些文件被改、是否影响你要复核的发现。
- 读文档仓 `git log` 近期提交与 docs/handoff/local-env.md、docs/development-workflow.md 的最新记录，整理一条「时间线」：每份审计报告读到的提交、每次发布（提交号、时间、release_id）、每次线上验证、每次相关修复提交。汇总中凡写“未发布”“没有任何功能上线”“未做真实环境验证”的句子，逐句对照时间线，列出过时的句子及依据。
- 若审计期间 HEAD 又变了，用 `git log --format='%h %ad %s' <各报告基线>..HEAD` 列出所有增量提交，并 `git show --stat` 看每个提交碰了哪些文件。

第 2 步：逐条复核（P0-01…P0-23、P1-01…P1-57、P2-01…P2-10、Q01…Q07，共约 100 条，分批做，每批先输出已完成部分）
对每条给出：
- 当前状态，四选一并附证据：「仍成立」（在 HEAD 上读到的 文件:行号 + 触发场景，能跑最小复现就跑）；「已修复」（修复提交号 + 修复后的代码事实 + 对应测试，若没有测试要说明）；「部分修复」（哪些子场景已修、哪些未修）；「已被替代」（根因或位置已变，说明新的位置）。无法判断的写「待证」并说明缺什么证据。不要仅凭提交说明或文档自述判定修复，必须读代码。

- 证据等级：静态读取 / 本地实验（HEAD 上实跑）/ 线上记录（注明文档提交号）/ 旧报告转述。只有前三种才算对 HEAD 的结论，“旧报告转述”不能当作仍成立。
- 严重度重评：同一缺陷在「还没发布」和「已发布」时严重度不同。请按当前已发布且有真实写入的现状重评，并写明理由（影响线上的真实数据？有无利用路径？受影响的角色范围？）。禁止因为“已经上线了”而无依据地升级，也禁止因为“只是测试环境”而降级——线上的 Base 和库是真实资源。
- 与线上证据的关系：文档仓里 2026-11-06 的线上验证记录（角色为 ID、速度、库存导入、连通性自检、采纳方案真实写入 T04 编号 29 / T05 编号 15、第四批测试数据已清理等）是否已经回答了汇总 6.3 里“必须在真实环境验证”的某一项？回答了的，把对应条目从“未验证”挪到“已有线上证据”，并标注证据来源与局限（例如只验证了正常路径、没做并发/故障注入）。

第 3 步：增量审计（新代码，别只复核旧问题）
对从各报告基线之后新增的提交，尤其是这些主题，按原专项提示词的标准做一次小范围审计：
- 幂等重放一族（新建航次、新增货物、修订 ETA、删除货物、采纳方案、主数据新增、靠船计划导入）：同键返回第一次的结果，是否记录请求指纹，同键不同载荷怎么办，首次请求失败或进行中时重放怎么办，重放是否绕过权限检查，结果是否包含不该返回的字段（金额）。
- 全局角色守卫（b27bd13）、用户目录改为按姓名搜 + 用户 ID 精确匹配（2463526）：是否仍有按姓名授权的路径，搜索歧义怎么处理。
- 读回自动编号、飞书配置清洗（首尾引号）、Excel 命名空间前缀、日历限宽、中文文件名乱码、系统时间差 8 小时、页面加载慢：每一项的修复是否完整、有没有引入新的边界问题（时区、编码、空值）。
- 靠船计划“只缺预计到港日期不再算日期异常”：这是 Leyinet 当天确认的新规则，核对代码是否严格只放宽这一项，不会让其他日期缺失也被放过，并且缺到港日期的行进入 CMR 计算时如何处理（是占用？还是跳过？是否标低可信？）。
- 新提交是否让此前“符合”的业务规则 1–12 回退。

第 4 步：重新运行质量门并如实记录
在 HEAD 上跑 npm test、npm run type:check、npx eslint server client/src --quiet、npm run smoke。Windows 默认 shell 下 npm test 可能发现 0 个用例仍返回成功，所以先确认实际发现并执行的用例数，再记录 通过/失败/跳过 数；若需指定 Git Bash 才能跑，写明命令。不要沿用旧报告里的 177/192/203 等数字。

第 5 步：输出
写入 docs/audit/10-revalidation.md，结构：
1. 基线与时间线：一段话说明本次复核基线，并列出汇总里已过时的表述及修正（用段落或清单，不用表格）。
2. 总体结论更新：在当前 HEAD 与当前线上状态下，原汇总的“不能联调、不能发布”结论是否仍成立？区分三个问题回答：能否继续真实联调、已上线的这个版本是否需要紧急处置、能否正式对业务放开使用。各给出阻断项。
3. 逐条复核表（这是给工程用的，可以用表格）：编号 | 原严重度 | HEAD 状态 | 证据与等级 | 引入/修复提交 | 重评严重度 | 变化原因。
4. 新发现：增量审计与复核中发现的、原汇总里没有的问题，按 P0/P1/P2 排序。
5. 线上现状风险清单：已上线版本里「现在就存在」的风险，每条写明可采取的临时缓解（例如关闭某自动任务、收窄某角色权限、暂停某导入），但只提建议，不要执行。
6. 修订后的整改顺序：只保留仍成立的和新发现的，重新分批，并标出哪些整改在线上版本也需要同步热修。
7. 仍无法判断的事项与所需证据。

一次读不完就先输出已完成部分和剩余清单，等我回复“继续”再接着做。
```

## 12. 持续审计提示词（代码持续推进时，每隔一段时间发一次）

```text
这是一次增量审计。上一次审计基线是代码仓提交 <上次基线 sha>（写在 docs/audit/ 最新报告的开头）。

1. 记录当前代码仓 HEAD 与工作区是否干净；用 `git log --format='%h %ad %s' <上次基线>..HEAD` 和 `git diff --stat <上次基线>..HEAD` 列出所有新增提交与改动文件。
2. 只审这段 diff 及其直接影响面（调用者、被调用者、相关测试、相关 SQL、相关页面），按总提示词的标准与业务规则 1–12 找缺陷。对 diff 里每个“修复”提交，确认它对应的历史发现是否真的关闭（读代码，不看提交说明），并检查是否引入回归。
3. 检查是否有提交修改了业务规则相关常量、阈值、泊位池、状态推导、权限矩阵、SQL 迁移、部署脚本，这几类改动一律单独列出并说明影响。
4. 若上次基线之后发生了发布，写明发布提交与时间，并区分「代码里存在」与「线上正在发生」。
5. 输出 docs/audit/增量-<日期>-<新基线短sha>.md：新基线、新增提交清单、已关闭的历史发现、新发现（P0/P1/P2）、回归、需要 Leyinet 决策的新增事项。没有新问题就明确写“本次 diff 未发现新问题”，并说明审到了哪些文件、没审到哪些。

约束同总提示词：只读，不改代码，不碰真实飞书和线上。
```

## 附：给 Leyinet 的使用提示

1. 审计可以并行：如果 Codex 支持多会话，1–9 之间互不依赖，可以各开一个会话分别粘贴「0」和对应的一段，最后在一个会话里粘贴「10」。
2. 一段跑不完就让它分批：每段末尾可以追加一句“若一轮读不完，请先输出已完成部分与剩余清单，我回复『继续』再接着审”。
3. Codex 的结论不是定论：审计报告里「疑似」的条目，拿回来让本机 Claude Code 逐条复现后再决定改不改。
4. 拿到 `docs/audit/00-summary.md` 后，**先发第 11 段做基线复核**，再把 `10-revalidation.md` 交给本机 Claude Code 整改；不要直接拿汇总报告整改，里面有已过时或已被修掉的条目。整改的代码仍然只在平台仓库提交。
5. 防止审计期间代码漂移的最稳办法：开审计前，你在本机另建一个固定提交的只读工作副本，让 Codex 审这个副本，开发继续在原目录推进。例如：
   `git -C C:\Users\董金\ssps-miaoda worktree add C:\Users\董金\ssps-audit <要审的提交sha>`
   审计结束后再删除：`git -C C:\Users\董金\ssps-miaoda worktree remove C:\Users\董金\ssps-audit`。这样所有报告读的是同一个提交，行号不会随开发偏移；之后用第 12 段只审新增的 diff。
6. 每次发布后立刻在 `docs/handoff/local-env.md` 记录发布提交与时间（现在已经在做），第 11 段依赖这份时间线判断“哪些是线上现状”。
