## 0. 先说结论（给 Leyinet 的白话版）

这两张图给的是一件很有价值的事：**把现在「一张表看十列、点一下跳一页、改一个字段要开弹窗」的做法，改成「一屏看完、原地改完、预警常驻」**。当前系统把同一条船的信息拆在 P01 工作台、P04 航次列表、P05 航次详情、P09 数据质量四个页面里，业务员完成一次「预测采纳 → 建计划 → 补节点 → 修 ETA → 看异常」要跳四到六次页面。设计稿把它们压进一个平面：主表平铺二十多列、点行内箭头展开详情、右侧常驻预警中心、底部一条汇总带，全程不换页。这个方向是对的，也是这次重构要拿到的主要收益。

但**不能照搬**。图里的产品叫「港口物流调度中心 / 发船计划管理」，登录身份是「调度主管-管理员」，而 SSPS 已锁定的定位是「给业务员用的智能发船预测系统，不做港口实时调度塔台、纯调度 Cockpit」。所以本次只借它的**信息组织方式和交互形态**，不借它的定位、数据能力、字段和状态。设计稿里的「ETA 船讯网」「AIS 数据正常」「气象服务延迟」「泊位冲突」「30 秒自动刷新实时数据」「批量审批」都属于一期能力之外或尚未定义的功能，照做会直接违反已锁定规则。

第二件事，`1.png` 很好，但它是一份**旧企微表的字段归属清单**，不是现在系统的字段清单。里面的「卸船进度」「等泊用时/小时」「共计用时/天」「第四次水尺」「2# 管带机」「X1 管带机吨位」「月份按离港算」等字段，在 `docs/schema/T05`、`T06` 里已经明确**删除或由公式替代**；里面「港务费 / 装卸费归仓储船务」也和 `T06` 已确认的「费用结算只有大宗采购部能看能改」冲突。所以「按岗位自由分配字段」不能理解为把这张清单搬到界面上，而要理解为：**以现有规格字段为准建一份字段目录，把每个字段挂到责任岗位，再由后端策略决定谁能看谁能改，用户只能在这份被裁剪过的目录里挑选自己视图里的列**。

第三件事，密度是**独立于皮肤的新维度**，不是第四套皮肤。现有三套皮肤（暖纸 / 夜墨 / 经典深蓝）是同构换色，`docs/design-system.md` 第 8 节明确「皮肤只允许覆盖颜色、阴影、边框色，几何必须复用暖纸」。因此紧凑档要落在共享样式单一源里，用 `data-density` 控制，三套皮肤共用；CMR 四档色阶、无数据灰色斜线、低可信标签在任何皮肤和任何密度下都不许变。

建议按 R0–R5 六期推进，先花一期把规格冲突和岗位映射定下来，再动代码。R0 不通过，不开 R1。

## 1. 差异分析（现状 vs 设计稿）

### 1.1 定位与用户

现状：核心用户是业务员（大宗采购部、商务海运部、仓储物流部），核心动作是「预测发船日 + 维护航次台账」。设计稿：面包屑「钢铁园区智慧派船系统 / 港口物流调度中心 / 发船计划管理」，当前用户「调度主管-管理员」，核心动作是「调度、审批、异常处置」。这是产品定位差异，不是视觉差异。按 `CLAUDE.md` 第 5–9 行，SSPS 不做调度塔台。

### 1.2 布局与页面跳转

现状是 11 个独立页面。P04 航次列表 10 列、每页 15 行、双行单元格、顶部独占一行的 4 张指标卡、独立筛选卡、独立明细卡；点整行跳 `/voyages/:id` 进 P05，P05 再用 5 个页签（基本信息 / 货物明细 / 卸船结算或销售扩展 / ETA 修订历史 / 变更日志）+ 4 个弹窗（登记节点 / 修订 ETA / 异常标记 / 登记水尺）承载编辑。P01 待办、P09 数据质量各自再跳回 P05 的 `?focus=` 字段。

设计稿是单页五区：紧凑标题栏与主操作（新建计划 / 批量审批 / ETA 重新计算 / 导出）、可折叠两行高级筛选、20+ 列高密度主表、行内箭头展开的分组详情（船舶信息 / 业务信息 / 货物信息 / 航次信息 / 调度信息 / 调度备注）、右侧常驻「ETA 预警中心」、底部一条汇总带。行内还有「修改 / 审批 / 航线」按钮。

### 1.3 信息密度

P04 主表 10 列，表头 + 行内双行信息（如「航次编号 + 船次号」「本港侧日期 + 装港侧/卸港侧」），字号 12–13px，行高约 56–60px；4 张指标卡和筛选卡又占掉约 200px 首屏；一屏有效信息约 10 行 × 10 列。设计稿 20+ 列、18 行一屏、行高约 32–36px，日期用「日期 + 时刻」两行、偏差与状态用彩色标签、指标全部压进底部 40px 汇总带，一屏有效信息约 18 行 × 22 列。按「一屏可见单元格数」粗算，密度差约 3–4 倍。

### 1.4 字段覆盖

P04 只暴露 10 个字段（航次编号 / 业务类型 / 船名 / 航线 / 总货量 / 本港侧日期 / 预计到达 / 状态 / 业务员 / 标记）。T04 的 41 个字段、T05 的 23 个字段、T06 的 17 组字段、T07 的 2 个字段全部塞在 P05 的页签里，不进入列表视野。设计稿则把计划 / 实际 / 偏差 / 动态 / 责任 / 优先级 / 更新时间 / 操作平铺到一行，行展开再补只读细节。**当前系统不是字段少，是字段被页面切碎了**。

### 1.5 编辑方式

现状：改一个字段 = 跳页 → 点操作按钮 → 弹窗或整页进入编辑态 → 保存 → 回列表。没有单字段行内编辑，也没有批量编辑。设计稿：行内按钮 + 行展开，原地完成。这直接对应「不要有太多页面跳转」的诉求。

### 1.6 预警与实时状态

现状预警是**散的**：P01 四块待办、P04 标记列的「待补 / ETA 过期 / 只读 / 重点关注」、P05 三条横幅、P09 数据质量清单、P02 的库存过期黄条。没有统一入口、没有分级、没有计数汇总、没有自动刷新、没有数据源健康状态。设计稿有统一的「ETA 预警中心」（顶部 4 严重 / 3 中风险 / 3 提醒，分组「严重异常·需立即处理」「ETA 延迟预警」，每条带等级、计划号、说明、偏差、时间，底部「自动刷新：30 秒」「全部预警」）、顶栏三个计数徽标（今日异常 7 / 加急任务 4 / 数据更新 09:32:15）、底部 8 格汇总带（今日发船 / 今日到港 / 实际到港同比 / ETA 异常数 / 偏航预警 / 待审批数 / 计划总数 / AIS 数据正常·泊位系统在线·气象服务延迟）。

需要如实说明：SSPS 一期的 ETA 是**人工修订**（K13，`D01 eta_revision` 留痕），没有 AIS / 船讯网 / 气象自动接入；也没有「泊位冲突」检测（`docs/open-questions.md` 里「池内同泊位日期重叠是否加进数据质量扫描」仍是未勾选项）。所以能做的是**预警聚合与统一呈现**，不是设计稿暗示的「实时 AIS 数据流」。界面措辞也要相应改成「数据更新于 HH:MM」，不要写「实时」。

### 1.7 视觉皮肤

设计稿是深蓝 ERP 风格，接近现有 `legacy` 皮肤；当前默认是暖纸 `paper`（并有 `midnight`）。高密度不是换肤的理由，两套语言可以共存：`legacy` 下紧凑档观感接近设计稿，`paper` / `midnight` 下保持现有 token。

## 2. 必须先解决的规格冲突（C1–C10）

按 `CLAUDE.md` 工作约定第 5 条「发现规格冲突时直接指出并给出建议的解决方式」，以下十项在 R0 逐条拍板，未确认前不得自行假定。

**C1 产品定位冲突。** 设计稿是调度中心，已锁定规则明确「不做港口实时调度塔台、纯调度 Cockpit」。建议：只借交互形态，页面名保留「航次列表 / 在途船运」，不叫「调度中心」；不引入调度员角色。

**C2 设计稿字段大量不在规格内。** 「船东」「优先级 / 加急」「ETA 船讯网」「ETA 偏差」「泊位冲突」「船舶动态（即将到港 / 在途 / 已批准 / 异常）」「审核 / 批量审批」「当前状态」「更新时间」「业务员」「合同号」等，多数不是 `T04–T07` 的字段或状态名。按红线「不得自创字段或状态」，建议逐项判定：能映射的映射到现有字段（如「业务员」→ T04 负责业务员、「合同号」→ T05 合同号、「更新时间」→ D02 变更日志最新一条、「当前状态」→ T04 船舶状态），不能映射的列入 R0 待确认清单，需要业务上真的要，就先改 `docs/schema/` 规格再开发。特别提示：T03 的「船型」枚举是「散货船 / 拖驳组合 / 集装箱船 / 杂货船 / 其他」，与设计稿的「好望角型 / 巴拿马型 / 超灵便型 / 灵便型」不是一套口径，不能混用。

**C3 `1.png` 的字段大部分已被新模型删除或替换。** 明确被 `T06` 删除的：卸船进度、系统/人工船舶动态（由状态替代）、实际卸船时间/天 与 /小时、等泊用时/天 与 /小时、共计用时/天 与 /小时（由 `T04` 公式「本港等泊 / 本港作业 / 实际航程」替代）、2# 管带机、第四次水尺、X1 管带机吨位、月份按离港算、可用管带机、价格（到岸价）、价格类型。建议：字段目录**只收 `docs/schema/` 现有字段**，`1.png` 仅作为「责任岗位归属」的历史依据，不作为字段清单；删除项若业务仍要，走规格变更。

**C4 责任岗位口径冲突。** `1.png` 的「采购业务员 / 仓储船务 / 大宗综合」与平台 4 个角色（业务员 / 部门主管 / 物流管理员 / 系统管理员）+ 3 个部门（大宗采购部 / 商务海运部 / 仓储物流部）不是同一套。更麻烦的是两处实质冲突：`1.png` 把「港务费 / 装卸费」归仓储船务，而 `T06` 第 25–30 行把它们划进「费用结算」，只有大宗采购部能看能改；`1.png` 把「滞期费率」归采购业务员，`T06` 也把它划进费用结算。建议：以 `T06` 权限分组和 `permission-matrix.md` 为准（已由 Leyinet 2026-11-04 确认），岗位映射表只做「显示上的责任归属」，不覆盖权限；这两处冲突写进 `docs/open-questions.md` 请业务确认。

**C5 字段级配置与金额隔离冲突。** 现有 `permissions.ts` 的 `canSeeMoney` 是**接口整体不返回金额字段**，变更日志对金额只记「已修改」，导出与错误信息同样不泄露。若「自由分配可显示字段」由前端配置驱动，会出现越权显示。建议：视图配置只能做后端策略的**子集**，无权字段在 `GET /api/ui/fields` 里根本不返回（不是前端隐藏），写接口对每个字段单独鉴权；越权字段直接 403，不静默丢弃。

**C6 状态口径冲突。** 设计稿的「船舶动态」四值不是 `docs/schema/status-rules.md` 的 8 个状态（待宣船 / 未到装港 / 装港等泊 / 装港装货 / 航行中 / 卸港等泊 / 卸港卸货 / 已结束）。建议：状态列一律用 `StatusTag` 渲染 8 状态，不新增状态；「异常」用 T04 异常标记 + 预警中心表达。

**C7 容量口径冲突。** 设计稿有「泊位冲突」「偏航预警」。已锁定规则 1 是「容量指标只用 CMR，任何界面不得使用其他容量口径」，且 `docs/open-questions.md` 里「池内同泊位日期重叠是否报」仍未确认。建议：一期只在预警中心做「同泊位日期重叠」的**只读提示**（数据来自 D04 靠船计划行，不新增容量口径、不影响 CMR 计算），且等 Leyinet 勾掉该待确认项后再启用。

**C8 皮肤与密度维度冲突。** `docs/design-system.md` 第 8 节规定皮肤只覆盖颜色 / 阴影 / 边框色，几何必须复用暖纸，验收第 8 条还要求 `[data-skin="midnight"]` 里不出现任何几何属性。建议：密度用独立的 `<html data-density>` 维度，几何规则落在 `app.css` 单一源（及 `app/client/src/ssps/ssps.css` 同源副本），不进 `skin.css`；新增 `scripts/check-density.mjs` 做几何与色阶回归检查。

## 4. 三层模型（本次重构的核心）

这是「按岗位或角色自由分配可显示 / 可编辑字段」能成立、且不破坏权限的前提。三层必须分开，不能混成一张前端配置表。

### 4.1 L1 字段目录 Field Catalog（后端单一真相源）

每个字段一条元数据：`key`、中文名、所属表与分组、值类型、渲染器（文本 / 双行日期 / 标签 / 偏差 / 进度 / 公式只读 / 金额掩码）、来源（业务录入 / 公式 / 规则引擎 / 外部只读）、责任岗位、敏感级别、是否可编辑、关联校验器。

字段**只能**来自 `docs/schema/T01–T08` 与 `D01–D12`，由代码常量定义，并在构建时用脚本对照规格文档校验（新增 `scripts/check-field-catalog.mjs`），防止自创字段。规则引擎输出字段（CMR、推荐窗口、断料日、可信度等）一律标 `engine / readonly`，任何生成式模型不得改写。公式字段（状态、本港侧、总货量、拼船、逾期、实际航程、本港等泊、本港作业）标 `formula / readonly`。

### 4.2 L2 字段策略 Field Policy（后端强制，不可配置）

把现有 `permissions.ts` 的航次级判断展开为字段级读 / 写矩阵：按「角色 × 部门 × 是否本人 / 本部门航次 × 航次业务类型 × 航次状态（历史只读、是否已抵卸港）」逐字段判定。金额字段继续走 `canSeeMoney`，**接口整体不返回**；费用结算字段继续走 `canEditMoney`；作业数据走 `canEditOps`；销售扩展走 `canEditSales`。

`GET /api/ui/fields` 返回的是**已按当前用户裁剪**的目录，每个字段带 `read / write / mask` 三个位。写接口对每个提交的字段单独过策略，越权字段 403。这样「自由分配」在任何情况下都不会变成「自由提权」。

### 4.3 L3 视图配置 View Profile（用户可自由定制）

配置内容：可见列集合、列顺序、列宽、冻结列数、密度档、默认分组与排序、默认筛选、预警订阅范围、行展开面板布局、汇总带显示项。

作用域四级：`system`（系统模板，只读）/ `role`（角色模板，系统管理员可写）/ `dept`（部门模板，系统管理员可写）/ `user`（个人，本人可写）。取值优先级 `user > dept > role > system`。个人配置只能隐藏和重排 L1∩L2 允许的字段，**不能新增字段、不能提权、不能显示金额**。

配置必须存服务端（跨设备、导出与审计一致），不能只放 `localStorage`；`localStorage` 只缓存皮肤与最近一次视图 ID。导出 CSV 时按 L2 策略裁剪列，不按个人视图裁剪（避免「换个视图就把金额导出去」）。

### 4.4 数据落点（需 Leyinet 批准规格变更）

`docs/schema/D-app-db.md` 目前只定义 D01–D12，且红线写明「不得自创表」。本次最小新增两张自有表，走和 W02 相同的流程：改 `scripts/build-ddl.mjs` → `lark-cli apps +db-execute` → `gen:db-schema`：

- **D13 `view_profile`**：`id`、`scope`、`scope_key`、`name`、`owner_id`、`payload`（JSONB：列 / 顺序 / 宽 / 冻结 / 密度 / 筛选 / 预警订阅）、`is_default`、4 个审计列、RLS。
- **D14 `alert_subscription`**（可选，一期可省）：用户对预警类型的订阅与静默设置。

**不建 `alert_event` 表**：预警由服务端在 `U03 / U05` 里现算聚合（D08 data_issue + D01/D02 + D04 靠船计划覆盖 + D11/D12 库存批次 + 现有 `etaStale` / `missingDeparture` 判定），避免冗余与不一致；若实测性能不够再物化。

角色与部门模板的初始化数据由 seed 脚本生成，不手填。

## 11. 风险与缓解

**性能**：24 列 × 2000 航次下，U03 若全量返回会重现「本机每条 SQL 1.4–4 秒、日历页 10 秒」的问题。缓解：服务端按可见列裁剪 + 分页 + `counts` 预聚合 + 虚拟滚动 + 当前批次快照缓存（W53 已提过）。

**越权**：字段级配置最容易出的错是「前端隐藏但接口仍返回」或「写接口静默丢弃越权字段」。缓解：L2 在接口层裁剪、写接口逐字段鉴权且越权直接 403；把这两条写进 smoke 与权限遍历测试。

**金额泄露面扩大**：行展开、行内编辑、导出、预警文案、错误信息都可能带出金额。缓解：R1 阶段就按 W52 清单重跑一遍，变更日志继续只记「已修改」。

**可读性**：暖纸皮肤低对比文字在 28–32px 行高下会明显吃力。缓解：`ultra` 档限制皮肤或补对比度，紧凑档正文不低于 12px、数字列继续 `tabular-nums`。

**规格漂移**：`1.png` 与 `docs/schema/` 差距较大，开发中最容易被「顺手加个字段」带偏。缓解：`check-field-catalog.mjs` 作为质量门，字段目录与规格文档不一致就构建失败。

**代码落点错误**：本仓库 `app/` 是冻结备份。缓解：R1 起所有改动只在 `C:\Users\董金\ssps-miaoda`，文档与原型在本仓库，按 `deploy-flow.md` 同步。
